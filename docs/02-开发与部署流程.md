# 从开发到部署：本项目学习路线

这份文档说明完整流程和分课安排。当前仍在 P0，下一项业务是 P1-01；脚本整理不代表验证码、登录或服务器部署已经完成。

用户已明确：此前项目只做过本机开发与检验，本轮希望亲手重写业务，同时完成 Git 和实际部署全过程。目标服务器为已有阿里云 ECS，Ubuntu，目前无网站或其他应用。具体 Ubuntu 版本、规格、连接方式和远程代码托管平台尚未确认。

Git 从业务重写前开始：先检查仓库状态、忽略规则和待提交文件，建立工程起点的基线提交，再逐项开发。每个小功能验证后提交；完成第一段业务后进行首次服务器部署，后续业务通过版本更新持续发布。Git 提交与服务器发布分别记录，不要求每次提交都立即发布。

## 1. 先认识两条流程

开发闭环：明确一个小需求 → 设计输入输出和数据 → 自己编码 → 本机运行 → 验证正常与失败场景 → 检查差异 → 记录并提交。

发布闭环：确定版本 → 执行测试和构建 → 检查发布产物与配置 → 在独立环境部署 → 验收 → 观察运行 → 必要时回滚。

业务不必全部写完才学习部署。先完成一个小功能，就能练习一次从源码到部署的全过程；尚未完成的接口继续明确返回“待实现”。

## 2. 一次只开发一个小功能

| 步骤 | 我们要做什么 | 留下什么结果 |
| --- | --- | --- |
| 需求 | 明确解决的问题、输入、输出、失败情况 | 一张小任务卡 |
| 设计 | 确定接口、涉及的类、MySQL 表或 Redis key、有效期 | 你能描述的数据流 |
| 编码 | 你写当前任务，我给提示和检查 | 一次可以解释清楚的修改 |
| 运行 | 启动依赖和后端，确认运行的是新代码 | 应用启动记录 |
| 验证 | 调接口并核对实际存储；覆盖正常、错误、边界场景 | 请求、响应、数据和 TTL 证据 |
| 检查与提交 | 查看差异、核对私有文件、运行适用检查 | 一个有明确用途的 Git 提交 |
| 记录 | 验证通过才更新学习进度 | 区分启动、依赖连通与业务完成 |

以 P1-01 为例：输入手机号；非法时拒绝；合法时生成六位字符串，存入 `dp:practice:login:code:<手机号>`，有效期两分钟；响应不返回验证码。实际验收要求见 [第一课](01-验证码与登录.md)，这里不代写实现。

## 3. 本机开发时，各个工具怎么配合

```text
浏览器：127.0.0.1:18080
  └─ Nginx：提供 HTML / CSS / JS / 图片
       └─ /api 请求去掉 /api 后转发
            └─ Spring Boot：127.0.0.1:18081
                 ├─ MySQL：127.0.0.1:3306 / dianping_practice
                 └─ Redis：127.0.0.1:16379 / DB 0 / dp:practice: 前缀
```

日常在 IDEA 运行后端，方便打断点；`scripts/user` 帮你启动依赖和前端。Agent 需要持续后台运行时使用 `scripts/agent`，详情见 [脚本说明](../scripts/README.md)。

遇到问题按链路查：页面请求地址 → Nginx 转发 → Controller 参数 → Service 业务 → 数据库/Redis → 响应。先确定故障在哪一层，再修改。

不要把三个层次混在一起：

| 层次 | 证据 | 不能据此认定的事情 |
| --- | --- | --- |
| 应用有响应 | `/practice/status` 返回工程标识 | 数据库、Redis 或登录正常 |
| 依赖连通 | 商户查询返回真实数据；Redis 认证与 PING 成功 | 验证码 TTL、登录复用等业务正确 |
| 业务完成 | 当前任务的正常、失败和过期等场景通过 | 后续阶段也已经完成 |

## 4. 从源码到 JAR：学习构建

Java 源码编译成 class；Maven 管理依赖并构建；Spring Boot Maven 插件生成可执行 JAR。当前前端是现成静态页面，没有单独的 npm 构建步骤。

在后端工程目录执行下面的学习命令；`verify` 会经过编译、测试、打包等前面的阶段，并执行项目已配置的检查：

```powershell
Set-Location D:\Projects\Java\Redis\hm-dianping
mvn clean verify
```

当前测试类为空，因此命令成功也不表示有业务自动化测试覆盖；必须另外完成任务的实际接口验收。后续按需求补有价值的测试。

`target/hm-dianping-0.0.1-SNAPSHOT.jar` 是当前后端产物。先在本机学习停止 IDEA 后用 `java -jar` 运行，理解服务器不需要 IDEA。运行工作目录仍为 `hm-dianping`，以便当前相对图片路径正常工作。

Maven 的 `deploy` 阶段是把构件发布到远程 Maven 仓库，不能用它代替服务器应用发布。参见 [Maven 构建生命周期](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html)。

## 5. 发布前要补齐的工程准备

当前配置和 Windows 脚本服务于本机练习。服务器演练开始时，先逐项完成并验证以下准备：

- **构建与运行环境**：记录使用的 JDK、Maven、依赖版本，在目标环境验证兼容性；编译目标 Java 8 不等于所有 JDK 组合都已验证。
- **配置与产物分离**：准备外部环境配置，明确激活的 profile。当前默认激活 `local`，服务器演练应显式选择发布环境配置。
- **检查 JAR 内的配置**：`.gitignore` 只约束 Git，不约束 Maven 资源打包。当前 `pom.xml` 没有排除 `application-local.yaml`，因此本地 JAR 可能含私有配置；正式发布前需要排除它、清理后重新构建，并检查 JAR 条目，不能直接分发当前本地包。
- **数据库变更**：本项目仅使用 `dianping_practice`。全新练习环境首次导入初始化 SQL；以后使用可追踪的增量脚本，不重复运行会重建表的初始化脚本。
- **持久化目录**：把上传图片、数据库与 Redis 数据放在版本目录以外；覆盖程序版本不应覆盖数据。
- **版本记录**：关联 Git 提交、产物校验值、配置版本和数据库变更；先确认工作区内容再选择提交，不把本机配置和日志加入版本库。

这些准备目前是学习任务，尚未实现发布专用 profile、打包排除规则或发布脚本。

## 6. 第一轮服务器演练：Linux + JAR + Nginx

目标是用户现有的阿里云 ECS（Ubuntu，目前无其他应用）。在这台服务器上学习运行 JAR，Nginx 提供静态页面并代理 API，MySQL 与 Redis 使用独立练习数据。先核实 Ubuntu 版本、规格、连接方式和已有组件，再决定具体安装与启动配置；不预设软件已经安装。学完手动发布，再学 Docker 和自动化流水线。

| 顺序 | 做什么 | 如何验收 |
| --- | --- | --- |
| 1 | 准备 Linux、已验证的 Java 运行时、MySQL、Redis、Nginx | 记录版本、目录、端口和运行用户 |
| 2 | 创建练习库、准备外部配置和数据目录 | 验证账号能访问练习库和指定 Redis |
| 3 | 上传已测试 JAR、静态页面和对应配置 | 校验产物、确认没有本机私有配置 |
| 4 | 在服务器前台运行 JAR，排查配置问题 | 状态接口、真实查询和当前业务场景通过 |
| 5 | 使用 systemd 管理后端进程 | 可启停、重启，能找到日志和失败原因 |
| 6 | 配置 Linux Nginx 的页面目录与 `/api` 代理 | 检查配置后加载，浏览器能完整访问 |
| 7 | 按入口、依赖、业务三层验收 | 记录成功与失败请求，检查写入的数据 |
| 8 | 演练更新和回滚 | 发布新版本，再恢复上个版本并重新验收 |

Spring Boot 的可执行 JAR 可以作为 Linux 服务运行，参见 [本工程版本的部署文档](https://docs.spring.io/spring-boot/docs/2.3.12.RELEASE/reference/html/deployment.html)。Nginx 静态文件、代理和配置加载见 [官方入门说明](https://nginx.org/en/docs/beginners_guide.html)。

### 从本机迁移时要理解的区别

- `127.0.0.1` 指当前程序所在机器。在服务器上浏览器仍访问自己电脑的 `127.0.0.1`，无法访问服务器；应使用服务器地址。
- Windows 的 `nginx.exe` 和 PowerShell 启停脚本留在本机；Linux 使用其自身的 Nginx 和服务管理方式。
- 当前 Nginx 只监听本机地址。供其他机器访问时调整服务器入口监听与网络访问规则；后端同机代理时可以继续监听回环地址，数据库和 Redis 无需随网页一起公开。
- Windows 图片绝对路径不能搬到 Linux。使用目标环境的独立上传目录，并同步配置后端写入位置与 Nginx 图片访问位置。
- 如果以后使用容器，容器里的 `127.0.0.1` 指该容器自身，需要重新设计组件连接地址。

首次服务器演练的具体命令、systemd 文件和 Nginx 配置，会在确定实际 Linux 环境后逐项编写并验证。

## 7. 更新发布和回滚也是开发的一部分

每次更新先确认版本、数据变更和恢复方式，再备份必要数据及保留旧产物。上传新版本后切换进程，完成入口、依赖和业务验收，再观察日志。

验收失败时切回旧产物及配套配置，并重新验收。代码回滚不会自动撤销数据库结构或数据变化，所以数据库变更必须事先考虑旧版本兼容性及恢复方案；不能用重跑初始化脚本作为回滚。

本轮先接受单机重启的短暂停机；多实例、健康检查与流量切换属于后续发布练习。

## 8. 分课安排

1. **Git 起点**：学习工作区、暂存区、提交；检查忽略规则和文件，建立业务重写前的基线。理解本地 Git 和远程代码仓库的区别，再配置选定的远程仓库。
2. **开发与提交闭环**：你完成 P1-01，亲手验证验证码及过期；我检查代码与证据，再带你检查差异并提交。后续小任务沿用这一流程。
3. **构建与本机发布**：理解 Maven、JAR、外部配置、日志及工作目录，完成发布产物排除私有配置的准备。
4. **阿里云 ECS 首次部署**：第一段业务完成后按第 6 节手动部署到 Ubuntu，完成浏览器到数据库/Redis 的验证链路。
5. **持续迭代与回滚**：开发后续业务，验证并提交，构建对应版本，更新服务器并验收；保留旧版本，模拟失败并恢复。
6. **自动化**：把已手动跑通的步骤转成脚本，再学习 Docker、CI/CD。

每课只推进一个可验证的小任务。业务进度仍记录在 `学习进度.md`；部署学习的验收证据在实际完成后另行追加，不提前勾选。
